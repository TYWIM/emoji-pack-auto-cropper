# 表情拼图裁切与格式导出：开发文档

## 1. 目标

用户上传一张包含多个表情的 PNG，系统识别每个表情的范围，按 1:1 裁切并允许用户确认名称和取舍，最终下载一个包含 PNG、GIF 与首图的 ZIP 文件。

这里的核心不是“切图片”本身，而是稳定地把一张不确定的输入转换为一个确定、可检查、可复用的文件结构。

## 2. 第一性原理拆解

需求可还原为五个不可缺少的事实：

1. 输入只有像素和文件名，系统不能假设拼图一定是几行几列。
2. “识别正确”无法只靠算法保证，用户必须能看见识别框并选择确定性回退方式。
3. 1:1 是源图裁切比例约束，300×300 是后期输出尺寸约束；源裁剪框尺寸由表情实际边界决定，不能把 300px 当作原图裁剪尺寸。
4. PNG 与 GIF 是同一批裁切结果的两种编码，不能分别裁切，否则尺寸和内容可能漂移。
5. 文件名和目录是交付协议，必须在服务端统一生成并校验，不能只依赖浏览器。

因此产品流程固定为：

```text
上传 PNG
  -> 自动检测（可切换规则网格）
  -> 显示 1:1 识别框和逐张预览
  -> 用户停用误识别项、填写名称
  -> 统一裁切为 RGBA 正方形
  -> 生成 300px PNG
  -> 从同一 300px 图生成 GIF
  -> 从第一张 300px 图生成 200px PNG
  -> ZIP 打包下载
```

## 3. 用户规则

### 3.1 输入

- 文件格式：仅 PNG。
- 单文件上限：25 MB。
- 解码后像素总量上限：4000 万，避免解压炸弹占满内存。
- 当前版本一次处理一张拼图。

### 3.2 识别

- 自动模式优先使用透明通道；没有有效透明通道时，从图片四周估计背景色并提取前景。
- 使用 OpenCV 的二值化、形态学闭运算、膨胀和轮廓检测组合相邻的表情主体与文字。
- 轮廓按从上到下、从左到右排序。
- 每个表情按实际视觉边界扩边并形成正方形裁切框；自动框允许少量重叠，但按同行、同列主体中心间距设置软上限，避免把相邻主体带入结果。手动修正不受该上限限制。
- 自动结果不合适时，用户可输入 1–20 行、1–20 列，以规则网格重新识别。
- 用户可停用误识别图片；编号按最终启用顺序重新连续排列。
- 原图支持 25%–220% 缩放、完整显示和滚动查看。
- 手动修正模式支持选中、移动、缩放、新增和删除正方形裁剪框；修改后的坐标随导出请求提交并由服务端再次校验。

### 3.3 命名

- 每张表情名称必须为 1–4 个汉字。
- 完整文件名：`表情名称_编号.扩展名`。
- 编号小于 10 时补零，例如 `开心_01.png`；从 100 开始自然使用三位数。
- 大文件夹名称由源文件名生成，用户可以修改；Windows 非法路径字符会替换为下划线。

### 3.4 图像输出

- 所有普通输出均为 300×300。
- 缩放算法为 Pillow LANCZOS。
- PNG 保留 RGBA 透明通道。
- GIF 为单帧 GIF，基础文件名与 PNG 完全一致，仅扩展名不同。
- “第一张”指最终启用并重新编号后的 `_01`，额外输出 200×200 PNG。

### 3.5 ZIP 目录协议

示例输入 `聊天拼图.png`，第一张命名“开心”，第二张命名“疑问”：

```text
聊天拼图_表情包/
├── PNG_300x300/
│   ├── 开心_01.png
│   └── 疑问_02.png
├── GIF_300x300/
│   ├── 开心_01.gif
│   └── 疑问_02.gif
└── 开心_01_200.png
```

ZIP 名称为 `聊天拼图_表情包.zip`。

## 4. 技术设计

### 4.1 选型

| 责任 | 采用方案 | 原因 |
|---|---|---|
| HTTP 与文件上传 | FastAPI + python-multipart | 成熟的类型校验和流式响应，不自行实现 multipart 解析 |
| 图像解码与缩放 | Pillow | 成熟支持 PNG、GIF、RGBA 与 LANCZOS |
| 视觉检测 | OpenCV | 使用经过验证的阈值、形态学和轮廓算法 |
| 数值处理 | NumPy | OpenCV 的标准数组表示 |
| 前端 | 原生 HTML/CSS/JS | 单页工作台规模有限，避免引入构建系统与框架运行时 |
| 打包 | Python zipfile | 标准库原生支持，避免引入额外归档依赖 |

这些组件只负责各自擅长的通用能力；项目代码仅实现本业务的编排、约束和交互，没有重写图像编解码、轮廓算法或 ZIP 协议。

### 4.2 模块边界

- `app/image_pipeline.py`：纯图像处理、命名校验和 ZIP 生成，可独立测试。
- `app/main.py`：HTTP 接口、临时会话和静态资源托管。
- `app/static/`：上传、预览、命名、启停和下载交互。
- `tests/`：检测、尺寸、文件名和目录协议回归测试。

### 4.3 接口

`POST /api/analyze`

- multipart 参数：`file`、`mode=auto|grid`、`rows`、`columns`。
- 返回：临时 `session_id`、原图尺寸和全部正方形框。

`GET /api/session/{session_id}/source`

- 返回标准化后的原始 PNG，用于画布预览。

`GET /api/session/{session_id}/crop/{index}`

- 返回对应 300×300 PNG 预览。

`POST /api/export`

- 提交临时会话、文件夹名称以及最终启用项和名称。
- 返回 ZIP 流。

临时会话仅保存在进程内存中，2 小时过期。服务重启后用户需要重新上传；此策略适合本地单机工具，也避免默认把用户图片持久化到磁盘。

## 5. 失败与边界处理

- 非 PNG、损坏图片、超大文件：上传阶段拒绝并显示具体原因。
- 透明 PNG：以 alpha 通道判断前景，尽量保留透明背景。
- 白底或纯色底：从四条边估计背景，允许轻微压缩噪声和色差。
- 自动检测为一个大区域或数量错误：切换规则网格重新识别。
- 表情靠近图片边缘：正方形向图内平移，不补造不存在的像素。
- 空导出、非法汉字名称、无效裁剪序号：前后端均拒绝。
- 会话过期：提示重新上传，不返回残缺文件。

## 6. 验收标准

1. 上传合法 PNG 后，界面显示原图、识别框和逐张 300px 预览。
2. 每个识别框严格为正方形且不超出原图。
3. 规则网格的行列数量改变后，识别数量等于 `行 × 列`。
4. 停用任意项后，其余文件从 `_01` 起连续编号。
5. 非汉字、空名称或超过四个汉字无法导出。
6. ZIP 中每个 PNG 和 GIF 都是 300×300，基础文件名一一对应。
7. 根目录仅额外包含第一张表情的 200×200 PNG。
8. PNG 透明区域在 PNG 输出中仍保持透明。
9. 桌面与窄屏都能完成上传、重新识别、命名和下载，不出现控件重叠。

## 7. 后续演进

- 若需要按语义自动命名，可新增视觉模型适配器，让模型返回每个裁剪图的 1–4 汉字候选；现有人工确认和服务端校验仍保留。
- 若需要不规则框纠正，可增加画布拖拽/缩放裁剪框，接口继续复用当前 `CropBox` 数据结构。
- 若部署为多人服务，应把内存会话替换为对象存储和带 TTL 的会话存储，并增加并发、配额和鉴权。
- 若需要动态 GIF，应明确帧来源、帧率、循环次数和透明色策略；当前输入是单张 PNG，因此 GIF 设计为单帧格式转换。
